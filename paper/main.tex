\title{\Large \bf Roll Back the Fault, Not the Future: Causal Recovery for Coding Agents with \system}
\author{Anonymous submission}
\maketitle

\begin{abstract}
Coding agents reuse files and tool results over long sequences of edits,
commands, and tests. An error can therefore affect both filesystem state and
agent context, making rollback necessary for continued execution.
Unfortunately, checkpoint and branch rollback also discard independent work
when affected and unaffected calls interleave.
We present \system, a causal recovery runtime built on Linux OverlayFS.
Given a user report naming the file to roll back, it follows file
dependencies and tool-result reuse to select
and validate a rollback set. This set guides filesystem reconstruction and
the removal of corresponding call/result pairs from agent context,
preserving independent work within and across turns. Recovery can therefore
reconstruct file states absent from any temporal checkpoint.
Across 400 controlled workloads with three repetitions per policy, \system
removes all affected calls and retains all independent work. Furthermore,
on matched successful tasks with SWE-agent and Codex, it reduces token use
relative to DeltaBox by 17.55--23.45\% on SWE-Bench Lite
and 25.39--44.69\% on Terminal-Bench. The real-task breakdown shows
lower agent-execution time in all twelve comparisons.
\end{abstract}


\section{Introduction}

Coding agents are increasingly used to automate software-engineering tasks
through extended interactions with development
environments~\cite{sweagent,openhands,autocoderover,hyperagent}. In these
workflows, agents edit code and execute commands, using the resulting
observations to decide how to proceed~\cite{react,toolformer}. Yet an
incorrect edit or command can disrupt the task and cause subsequent actions
to build on an erroneous result. Worse still, the effects of the mistake can
persist even after it is recognized, leaving the agent to repair affected work
before making further progress~\cite{agentrewind,planarian}. Rollback is
therefore essential for removing these effects and restoring a valid state
from which the agent can continue~\cite{try-osdi26,branchfs,crab}.

To support rollback, existing systems stage effects or restore checkpoints.
In particular, effect-staging systems isolate filesystem changes for later
application or discard~\cite{try-osdi26,branchfs,cordon}. When selecting
file effects to discard, the caller also has to identify dependent calls
and observations to remove. By comparison, checkpoint/restore systems save state for later
restoration~\cite{rollbacksurvey,dmtcp,waypoint,deltabox}. Building on
these mechanisms, recent agent runtimes select checkpoint state from turn effects~\cite{crab}, restore
consistent environment versions~\cite{planarian}, or recover aligned
filesystem and agent-context checkpoints while retaining lessons~\cite{agentrewind}.
However, restoring an earlier checkpoint discards later independent updates,
while rolling back a whole branch loses its independent changes.

Our motivational experiments (Section~\ref{sec:motivation}) show that
the DeltaBox recovery scope discards 56.90\% of valid work on average across 400
fixed trajectories, even with exact fault information. Moreover, dependent
calls interleave with independent work in 86.8\% of 946 complete clean agent
traces. These observations show that existing recovery policies discard
substantial valid work. Our goal is to retain independent progress while
undoing affected file changes and removing the associated tool results
from agent context.
To this end, we present \system, a causal recovery runtime for coding
agents. The key idea is to \textbf{let dependencies among tool calls
determine the recovery boundary across filesystem state and agent context}.
The user identifies the file whose changes should be rolled back.
\system selects its mutations since a reference checkpoint and follows
file dependencies and tool-result reuse to derive one rollback set.
An isolated trial checks the expected file state and command/result residue
before live recovery. The runtime restores affected file objects and
removes the corresponding calls and results from agent context while preserving
independent progress. Consequently, recovery can preserve independent calls
within and across turns and combine earlier file versions with later valid
updates, even when that combination never existed at a checkpoint.

However, designing a filesystem that supports causal rollback poses three
key challenges.
1) A user can identify a problem file without knowing which calls depend
on it. \system follows both file and result dependencies from the file's
mutations, then checks the resulting rollback state before resuming execution.
2) The desired file state may be absent from every checkpoint. To
reconstruct it, \system restores selected object versions, metadata, and
deletion state in OverlayFS while retaining independent updates.
3) A single agent turn can contain both affected and independent calls.
Accordingly, \system uses shared call identifiers to remove affected
calls and results from the next model request while retaining independent
pairs within the same turn.

We implement \system on Linux OverlayFS and integrate it with SWE-agent
and Codex. In controlled
experiments on 400 workloads, with three
repetitions per policy, \system removes all affected calls while retaining
all independent work. Beyond these controlled workloads, \system reduces token consumption
on real-world SWE-Bench Lite~\cite{swebench} and Terminal-Bench~\cite{tbench}
tasks relative to DeltaBox by 17.55--23.45\% and 25.39--44.69\%,
respectively, on matched successful task pairs across the two agents.
On the same real tasks, the breakdown shows lower agent-execution and
setup/replay time relative to DeltaBox.

This paper makes three contributions:
\begin{itemize}
  \item We quantify the valid work lost when recovery boundaries include
        calls independent of an error, and show that dependent calls
        commonly interleave with independent work in real agent traces
        (Section~\ref{sec:motivation}).
  \item We design and implement \system, which combines file dependencies
        and tool-result reuse to select and validate rollback sets. The
        selected set guides selective object restoration and updates
        agent context, preserving independent calls within and across turns
        (Section~\ref{sec:design}).
  \item We evaluate recovery correctness, preserved work, runtime overhead,
        and model cost on controlled and real-world workloads
        (Section~\ref{sec:eval}).
\end{itemize}


\section{Background}
\label{sec:background}

\subsection{Stateful Coding-Agent Execution}

ReAct interleaves model reasoning with actions and observations from an
external environment~\cite{react}. Coding agents such as SWE-agent and
OpenHands repeatedly inspect repositories,
edit files, invoke shell commands, and run tests~\cite{sweagent,openhands}.
Each tool call can consume source edits, generated artifacts, or configuration
changes left by earlier calls. The filesystem therefore carries
progress across the task. At the same time, the agent context---the messages
supplied to subsequent model requests---records calls and their results.
A reported test outcome, for example, describes a particular filesystem
version. After recovery, the observations supplied to the agent should
therefore describe the file state that remains.

Toolformer incorporates API results into subsequent token
generation~\cite{toolformer}. Reflexion retains textual feedback for later
attempts, while MemGPT moves information between memory tiers and the
active model context~\cite{reflexion,memgpt}. Software-engineering systems such as
AutoCodeRover, Agentless, and HyperAgent combine localization, editing, and
validation~\cite{autocoderover,agentless,hyperagent}.
SWE-Bench and Terminal-Bench evaluate agents through executable repository
and command-line tasks~\cite{swebench,tbench}.
SWE-Gym trains agents and verifiers in executable repository
environments~\cite{swegym}. FeatureBench and SWE-EVO extend evaluation to
complex feature development and sustained, multi-file software
evolution~\cite{featurebench,sweevo}. These workflows accumulate both modified
files and observations that later decisions reuse.

An error can affect both forms of state. A later tool call can read an incorrect
file, or the model can reuse an incorrect value from a tool result in a later
request. These effects therefore extend to subsequent calls that
consume the faulty state or reuse affected results. Recovery determines how
much valid work survives by choosing which calls to withdraw from both
histories.

\subsection{Recovery Support for Stateful Agents}

Classical rollback-recovery protocols use checkpoints and logs to resume
consistent execution after failures~\cite{rollbacksurvey}. Process
checkpointing and file transactions provide underlying state-management
mechanisms~\cite{criu,dmtcp,valor,txfs}. We classify agent-facing recovery
interfaces by the scope of their rollback: selected effects, temporal
checkpoint, turn checkpoint, and whole branch.
Figure~\ref{fig:motivation-rollback-example} illustrates these four scopes
on six calls across three turns. Call 4 writes an incorrect value to A,
and Call 6 reads it; the updates to B, C, D, and E remain valid.

  \small\emph{Red calls are faulty or affected; green calls are independent.
  Four outline styles mark selected effects, a temporal suffix, a
  turn-boundary suffix, and the whole branch. The arrow denotes dependency.}}
  \label{fig:motivation-rollback-example}
\end{figure}

\textbf{Selected effects.}
Semisolates let callers inspect, selectively apply or discard, filter, and
stack filesystem effects~\cite{try-osdi26}. Their tracing interface also
extracts dependencies. In the example, discarding the faulty write to A
alone leaves the later read affected. Discarding a file effect therefore
also calls for a decision about which dependent agent calls and
observations to withdraw.

\textbf{Temporal checkpoint.}
These interfaces restore a saved environment version. Waypoint captures filesystem and
process state together~\cite{waypoint,waypoint-project}. DeltaBox pairs
DeltaFS layer switching with DeltaCR process restoration to return both
forms of state to the same checkpoint~\cite{deltabox}.
Planarian also coordinates supported remote effects through compensating
operations~\cite{planarian}. In the example, restoring the point before
Call 4 withdraws the last three calls, including the independent update to E.

\textbf{Turn checkpoint.}
These interfaces place recovery points at agent-turn boundaries. Crab uses
observed OS effects to select the state to capture and overlaps capture
with execution~\cite{crab}. AgentRewind restores aligned filesystem and
agent-context checkpoints and retains lessons from abandoned
attempts~\cite{agentrewind}. In the example, restoring the start of Turn 2
also removes the independent update to D.

\textbf{Whole branch.}
These interfaces discard a complete speculative branch or transaction.
BranchFS provides nested copy-on-write branches with commit/abort~\cite{branchfs}.
Cordon stages local mutations and external effects, tracks result lineage,
and validates the composed flow before commit; local rollback restores
pre-transaction state~\cite{cordon}. Whole-branch recovery in the example
withdraws all six calls, including all four independent updates.

Other mechanisms support isolation and dependency-aware execution.
Sandlock confines agent-invoked code with a copy-on-write work
directory~\cite{sandlock}. hS uses dependencies to revoke and re-execute
affected speculative subprocesses while preserving sequential
semantics~\cite{hs-osdi26}. Provenance systems record how outputs derive
from earlier actions~\cite{pass,beep}; RETRO uses an action-history graph
to undo unwanted actions and selectively re-execute affected legitimate
actions~\cite{retro}.

Table~\ref{tab:granularity} compares the scopes on two recovery goals:
removing all affected calls and preserving all independent work. A turn
checkpoint policy can preserve unaffected turns, but loses independent
calls inside withdrawn turns. A temporal checkpoint policy can also
discard independent work in later unaffected turns. State coverage is
separate from rollback scope:
Waypoint, for example, restores files and processes, whereas AgentRewind
restores files and agent context.

\section{Observations and Motivation}
\label{sec:motivation}

\subsection{Recovery Loss and Dependency Structure}
\label{sec:motivation-observations}

The recovery scopes in Section~\ref{sec:background} can discard valid work
when independent calls execute alongside calls affected by an error.
Our goal is to remove file changes and observations produced by affected calls
while preserving independent progress. We examine the resulting loss under
existing recovery scopes, explain why execution order alone cannot identify
affected calls, and check whether real agent trajectories exhibit the same
interleaving.

\textbf{Methodology.}
To isolate recovery loss from agent randomness and fault-localization
errors, we use 400 scripted trajectories without an agent or LLM for the
first two observations: 100 vary task length, 90 vary fault position, and
210 vary dependencies and interleaving. Each turn has 16 calls. We implement
the recovery scopes associated with the works in Table~\ref{tab:granularity}
on a common OverlayFS runtime and label the controls by those work names.
DeltaBox withdraws the faulty call and all later calls, Crab withdraws
affected turns, and BranchFS withdraws the entire branch. All three remove
all affected calls. The \trycmd control withdraws only the faulty call,
without expanding to dependent calls.

For \system, the user specifies the file whose changes should be rolled
back, without identifying a faulty step. The runtime derives the
affected-call set from that file's recorded mutations and their file and
tool-result dependencies. The controls receive the exact faulty step; Crab
also receives the exact affected turns. For each control, we choose the
smallest withdrawal set its rule permits, so localization errors do not
reduce retention. We measure the affected work removed and the collateral
loss (independent calls discarded). Retention percentages use deterministic
token weights. As a reference target, an \emph{Ideal oracle} uses the
generated dependencies to roll back the erroneous operation and all its
dependent effects while retaining every unaffected file change and agent
observation, removing all affected work with zero collateral loss.

\textbf{Observation \#1: Existing recovery strategies waste substantial valid work.}
Removing every affected call can still discard independent progress.
Figure~\ref{fig:motivation-coarse-waste} uses 100 fixed trajectories, with
ten cases at each length from 16 to 160 calls and 16 calls per turn.
Every case has exactly four affected calls; the remaining calls are
independent work that recovery could preserve. Keeping the number of
affected calls fixed lets us examine whether longer executions cause more valid work
to be discarded.

Figure~\ref{fig:motivation-coarse-waste}(a) shows that the loss grows with
execution length. From 16 to 160 calls, the average number of independent
calls discarded rises from 12 to 56.8 for Crab, from 8 to 116
for DeltaBox, and from 12 to 156 for BranchFS.
Figure~\ref{fig:motivation-coarse-waste}(b)
shows the total calls rolled back. At 160 calls, the three controls remove
60.8, 120, and 160 calls, respectively, to clear just four affected calls.
All calls removed beyond those four are valid work lost during recovery.
The Ideal oracle discards no valid calls and rolls back exactly the four
affected calls at every trajectory length.

Across all 400 cases, Crab, DeltaBox, and BranchFS discard 54.02\%, 56.90\%, and 100\% of valid work on average.
These losses occur with exact fault information. Even Crab,
given the exact affected turns, discards the independent calls within
those turns.

\trycmd discards no independent work but removes only 17.03\%
of affected calls on average. It clears the entire affected set in only
10 of 400 cases (2.5\%), all with no dependent calls.

To explain these losses, we next examine where independent calls occur
relative to calls affected by the error.

\textbf{Observation \#2: Calls executed after an error are not necessarily
affected by it.}
In Figure~\ref{fig:motivation-rollback-example}, the update to E occurs after
the faulty write to A but does not depend on it. The later read of A does.
Both calls execute after the error, but only the read consumes the faulty
state. Rolling back both would discard the valid update made by E.

In 390 of the 400 trajectory cases (97.5\%), returning to a checkpoint cannot
remove every affected step without also discarding valid work. Only the
remaining ten cases allow temporal rollback to remove all affected steps
and preserve all independent work.

Figure~\ref{fig:motivation-dependency}(a) varies the percentage of later calls
that depend on the faulty call, from 0\% (none) to 100\% (all), in an 80-call
execution. This sweep uses 210 fixed trajectories, ten per point, with exact
fault information. The x-axis gives the fraction of later calls affected by
the faulty call; Figure~\ref{fig:motivation-dependency}(a) reports the
minimum valid work discarded, using the deterministic token weights.
With no dependent later calls, Crab discards 18.99\%
of valid work and DeltaBox discards 74.68\%.
DeltaBox removes exactly
the affected calls only in the ten fully dependent cases, losing independent
work in the other 200 cases.

Figure~\ref{fig:motivation-dependency}(b) shows why this loss occurs.
The execution length and fault position stay fixed, so DeltaBox
always removes 60 calls. Yet the actual affected set grows from one to 60
calls as dependencies increase. At 0\%, DeltaBox discards 59 valid
calls along with the faulty call; only at 100\% are all 60 calls affected.
The Ideal oracle follows the affected set throughout. Thus, executing a
call after the error does not mean that the call depends on it.

The Ideal oracle discards no valid work throughout the sweep. The gap is
largest when many later calls are independent of the error. Selection by
dependency preserves those calls, whereas temporal rollback removes
everything after a point in time. The controlled cases establish this opportunity; the next
observation asks whether real agent executions contain the same interleaving.

\textbf{Observation \#3: Dependencies interleave with independent work
in real agent executions.}
The controlled cases show why a time boundary can include valid work. We
next check whether the same structure arises when agents autonomously solve
benchmark tasks. SWE-agent and Codex each run 300 SWE-Bench Lite~\cite{swebench}
and 241 Terminal-Bench~\cite{tbench} tasks with live LLM calls and no injected
faults. All 1,082 runs finished. We analyze 946 complete traces, including
failed attempts and traces with no recovery opportunity; the 38 partial traces and
98 invalid captures are reported separately.

Offline analysis combines file and result dependencies, recorded parents,
and opaque-context barriers. Useful calls access task files or build
artifacts, or return nonempty task observations; adapter polling, patch
retrieval, and submission are excluded. For Codex, read tracing covers the
traced processes and their descendants; failed lookups do not count as
evidence that a directory exists.
Interleaving requires useful calls $i<j<k$: $i$ changes files or returns an
observation, $k$ depends on $i$, and $j$ lies outside the dependent closure of $i$.

Figure~\ref{fig:motivation-native-opportunity} reports the recorded
dependencies for both agents and benchmarks.
Figure~\ref{fig:motivation-native-opportunity}(a) considers only file
dependencies. Figure~\ref{fig:motivation-native-opportunity}(b) considers
both file dependencies and dependencies carried through agent context,
where later calls reuse earlier tool results. It counts traces in which
independent work occurs between dependent calls. The two panels measure
different properties: (a) counts traces with file dependencies, while (b)
counts interleaving under the combined file and result graph.
Both use all complete captures as the denominator, including failed task
attempts and zero-opportunity traces. SWE and TB denote SWE-Bench Lite
and Terminal-Bench; $N$ gives the numbers of complete traces for SWE-agent
followed by Codex.

File dependencies occur in 245/297 SWE-agent and 256/257 Codex SWE-Bench
traces (82.5\% and 99.6\%), and 125/223 SWE-agent and 149/169 Codex
Terminal-Bench traces (56.1\% and 88.2\%; Figure~\ref{fig:motivation-native-opportunity}(a)). Thus, the effects of a call
are reused by later calls in both benchmarks and agent systems.

Figure~\ref{fig:motivation-native-opportunity}(b) shows dependency interleaving in 266/297 SWE-agent and 257/257
Codex SWE-Bench traces (89.6\% and 100\%), and 145/223 SWE-agent and
153/169 Codex Terminal-Bench traces (65.0\% and 90.5\%). Overall,
821/946 traces (86.8\%) contain a dependent pair separated by independent
task work. If recovery withdraws file effects or an observation produced by
a call, rolling back to before that call also removes the intervening
independent work. The mismatch in Observation~\#2 is therefore common in
autonomous benchmark trajectories.

\subsection{Motivation}
\label{sec:recovery-challenges}

Together, these observations motivate recovery that follows dependencies
across both files and tool results. Given a user-specified file, the goal
is to withdraw its mutations since a reference checkpoint and their
dependent calls while preserving independent file updates and observations.

\textbf{Attempts.}
The recovery scopes examined above fall short in different ways:
1) The Crab scope clears affected turns but also discards
independent calls within them; 2) the DeltaBox and BranchFS scopes remove
affected work together with independent progress. Even with exact fault
information, these scopes incur the loss shown in
Figures~\ref{fig:motivation-coarse-waste} and~\ref{fig:motivation-dependency}.

\textbf{Insight.}
An error can spread from a file into a tool result and back into a later
file change, while independent calls occur in between. Following file
dependencies alone can therefore miss calls that reuse a returned value.
Evidence from both channels guides the selection of calls to withdraw.
Tool calls provide a practical recording unit: each call links
file accesses and mutations to a result that the agent can reuse.

\textbf{Challenges.}
Realizing this strategy raises three questions:
1) How can recovery derive and check a rollback set from a user-specified
file when its effects propagate through both file state and reused tool results?
2) How can the filesystem combine historical versions of affected
objects with current independent updates, when no checkpoint contains the
desired state?
3) How can the same rollback set update the agent context, removing
withdrawn calls and results from mixed turns while preserving independent
observations, so the next model request matches the restored filesystem?
Section~\ref{sec:design} answers these questions through rollback-set
selection, filesystem reconstruction, and agent-context alignment.

\section{AgentTX Design}
\label{sec:design}
\label{sec:aet-model}
\system coordinates filesystem and agent-context recovery through one
rollback set $S$. Recovery starts with a user report naming the file or
files to roll back. The reference checkpoint denotes the state after a
selected call; the default is the committed boundary. The report identifies
a file-history range to withdraw, without identifying a faulty step or
deciding which edit was semantically wrong.

\begin{figure}[H]
\centering
\includegraphics[width=\linewidth]{FIG-AgentTX-Overview.pdf}
\caption{\textbf{Execution and selective recovery in \system.}
\small\emph{A user identifies the file to roll back. Shared call identifiers
connect dependency capture, saved
versions, and conversation records. The selected set $S$ drives both
filesystem restoration and agent-context updates.}}
\label{fig:overview}
\end{figure}

In Figure~\ref{fig:overview}, a persistent worker executes
calls in an OverlayFS merged view over a read-only lower baseline $L$ and
writable upper state $U$~\cite{overlayfs}. Tool-dispatch hooks integrate
SWE-agent and Codex; shared call identifiers link the file-effect ledger,
saved versions, and conversation log. The three challenges in
Section~\ref{sec:recovery-challenges} lead to three design points:
\begin{itemize}
\item \textbf{Select and validate $S$ via file and result dependencies.}
Start from the reported files' mutations and audit their joint dependency
closure in an isolated branch (Section~\ref{sec:rollback-set}).
\item \textbf{Control filesystem recovery in user space.}
Retain object history incrementally, manage explicit OverlayFS checkpoints,
and restore affected objects alongside current independent updates
(Section~\ref{sec:userspace-fs}).
\item \textbf{Synchronize agent context via shared call identifiers.}
Use $S$ to remove withdrawn calls and results while preserving independent
observations within and across turns
(Section~\ref{sec:context-reconstruction}).
\end{itemize}

\subsection{Rollback Selection via File and Result Dependencies}
\label{sec:rollback-set}
A fault can propagate through a file, a reused tool result, or both.
Figure~\ref{fig:dependency-closure} expands step 2 of
Figure~\ref{fig:overview}: the reported file's mutations seed joint
dependency closure, an isolated residue audit checks the resulting state,
and the selected $S$ drives both filesystem restoration and agent-context synchronization.

\textbf{Capturing dependencies across both channels.}
Each exposed tool call receives an identifier linking its command, file
effects, version references, and call/result pair; a submitted script is
one recording unit. \texttt{strace}~\cite{strace} records reads and failed
lookups, while upper-state comparison identifies writes and deletions.
Table~\ref{tab:dependency-rules} gives the direct edges
$E_i\rightarrow E_j$ for $i<j$, where $R$, $W$, and $N$ denote reads or
access checks, mutations, and failed lookups. Related state includes path
hierarchies, resolved symlink ancestors, and cataloged object identifiers,
including known hard-link aliases; renames contribute both names.
The conversation log filters common and short strings from tool results
and matches distinctive values against later arguments to add result edges.

\input{tables/dependency-rules}

\textbf{Selecting calls via joint dependency closure.}
The controller normalizes the reported paths, resolves known aliases, and
selects all active mutations of those files after the reference checkpoint
as roots $B$. It alternates forward expansion through file and result edges
until neither adds a call. In Figure~\ref{fig:dependency-closure}, a report
for f selects E3 and E4; file effects lead to E6, and E3's reused result
leads to E7, whose output E8 reads. The resulting
$S=\{\mathrm{E3},\mathrm{E4},\mathrm{E6},\mathrm{E7},\mathrm{E8}\}$
preserves independent E5 and captures the chain across both graphs.
The controller derives one scope from the report; it does not enumerate
faulty-step candidates or use task-test success to choose where to stop.

\textbf{Checking recovery before model continuation.}
The filesystem controller supplies compatible pre-mutation versions for
overlapping paths written or deleted by $S$
(Section~\ref{sec:userspace-fs}). Before application, the runtime freezes
the graph, active call/result identifiers, and expected saved file entries.
It applies the plan in an isolated branch and checks for residual selected
calls, visible results, dangling dependencies, and mismatched file state.
Reported files must match the reference checkpoint; retained entries and
the lower baseline must remain unchanged. Missing history, incompatible
versions, or a failed check make recovery inconclusive. After a clean trial,
the runtime verifies that the history has not changed, applies the same
frozen plan, and repeats the audit before model continuation.
The official task verifier evaluates subsequent repairs separately.

\subsection{Filesystem Recovery via User-Space Control}
\label{sec:userspace-fs}
\label{sec:version-retention}
\label{sec:selective-reconstruction}
The selected calls can require a combination of file states absent from
every checkpoint. The user-space controller in \system translates $S$ into
object versions and restoration operations, using native Linux mount and
file interfaces. OverlayFS supplies the merged view and copy-on-write
behavior; the controller manages version history, checkpoint lifetimes,
and selective restoration.

\textbf{Retaining history via changed entries.}
Figure~\ref{fig:version-capture} separates incremental object history from
explicit checkpoints. Each logical recovery point references its parent
and records changed paths, contents, metadata, and deletion state;
unchanged state reuses its existing version. Immutable contents are shared
in the version store, while the active upper keeps separate writable
copies. E3 and E4 add f1 and f2; E5 adds g1 without copying earlier versions.
Recovery follows parent references to retrieve selected objects, applying
deltas where needed. A complete historical tree is materialized only when
requested, avoiding repeated directory cloning and a new mounted
checkpoint for every call.

\begin{figure}[!t]
\centering
\includegraphics[width=\linewidth]{figures/design-workflow/AgentTX-Version-Capture.pdf}
\caption{\textbf{Incremental history and explicit checkpoint creation.}
\small\emph{Changed entries extend object history. An explicit checkpoint
retains the old read-only view and starts a fresh writable upper; retained
mount references are released at commit or close. Solid arrows show flow;
dashed arrows associate saved file state with history records.}}
\label{fig:version-capture}
\end{figure}

\textbf{Managing checkpoints via retained mounts.}
For an explicit storage checkpoint, the caller quiesces writers. The
controller makes the current view read-only, retains a mount reference,
detaches the view, and mounts a fresh writable upper over the frozen layers.
In Figure~\ref{fig:version-capture}, checkpoint C1 references U0 and L
after E5, and execution continues in U1. Retaining the mount defers
superblock destruction to commit or close, while file data stay in their
existing layers. Section~\ref{sec:eval-file-commit} measures checkpoint
latency and the complete workflow, including reference release and cleanup.

\textbf{Reconstructing state via compatible object versions.}
The controller groups overlapping paths mutated by $S$, placing a selected
directory and its children together. For each group, it resolves the
nearest compatible saved state before its earliest selected mutation and
rejects retained mutations that overlap a group after its earliest selected
mutation. Earlier retained writes remain in that group's saved state.
Groups may use different
historical versions; paths outside them retain their current state.
In Figure~\ref{fig:design-workflow}, f comes from V0 before E3, h from V1
before E6, and p from V2 before E7. V0 has correct f0 but predates g1;
V1 and V2 contain g1 together with affected f2. Selecting individual
entries preserves the required f0/g1 combination.

After isolated validation, the runtime checks the frozen history signature,
stops the worker, and applies the same $S$ and saved versions in the live
session. It restores the contents, metadata,
and deletion state of each group in the upperdir. Removing an upper entry
exposes its lower version or leaves the path absent. Removing f2 and the
whiteout hiding h therefore exposes f0 and h0; removing p1 makes p absent,
while independent g1 stays in $U$. The runtime refreshes mount scaffolding
and filesystem tracking without replaying retained commands, then applies
the same selection to agent context.

\label{sec:context-reconstruction}
Recovery also removes observations of withdrawn effects
from the next model request. Shared identifiers let \system apply the same
$S$ to file-effect records and agent-visible call/result pairs, retaining
independent observations from partially withdrawn turns.

After restoration succeeds, selected ledger steps and their call/result
spans become inactive, with full records retained for audit. In the mixed

the next model request. If older history is summarized to meet the context
budget, summaries are rebuilt from active spans so withdrawn results do
not reappear through compaction. Saving the ledger and conversation
together in session metadata keeps subsequent execution tied to the same
recovery decision.

\subsection{Correctness of Selective Recovery}
\label{sec:recovery-correctness}
Let $F$ be the normalized files named by the user, $c$ the reference
checkpoint, and $X_c$ its filesystem state. Let $H$ be the finite active
history, $G$ the union of recorded file and result edges, $W_i$ the mutation
footprint of $E_i$, and $V_i$ its pre-call saved versions. Write
$W(A)=\bigcup_{E_i\in A}W_i$. Edges point forward in call order. Footprints include
contents, supported metadata, deletions, related paths, and known aliases;
$\bowtie$ denotes footprint overlap. Calls execute serially over a fixed
lower baseline, with no untracked writers during recovery. Saved versions
faithfully represent this history, and file effects and call/result records
share identifiers. To cover actual propagation, $G$ must contain all true
dependencies within this managed state. State equality covers contents,
supported metadata, presence, and active call/result records.
Distinctive-string matching alone does not establish capture completeness.

Algorithm~\ref{alg:causal-rollback} computes the report's scope and applies
it. $\operatorname{Audit}$ checks frozen expected versions, checkpoint
files, active identifiers, retained entries, and the lower baseline as
described in Section~\ref{sec:rollback-set}. Its acceptance condition is
independent of the original task's test outcome.
Write $Z=(X,C,\operatorname{Active}(H))$. The fixed transformation $T_S$
restores each group from $V_{m(p)}$, projects records onto $R$, and marks
$S$ inactive. $\operatorname{Fresh}(A)$ checks the frozen history signature;
$\bot$ denotes rejection or inconclusive recovery.

\begin{algorithm}[H]
\caption{File-scoped recovery}
\label{alg:causal-rollback}
\footnotesize
\textbf{Input:} $F,c,H,G,V,Z$
\begin{enumerate}[label=\arabic*:,ref=\arabic*,leftmargin=1.7em,labelsep=.4em,topsep=2pt,itemsep=0pt,parsep=0pt]
\item $B\gets\{E_i\in H\mid i>c\ \land\ W_i\bowtie F\}$ \label{algline:file-roots}
\item \textbf{if} $B=\varnothing$ \textbf{return} $\bot$
\item $S\gets\operatorname{Reach}_G(B)$ \label{algline:closure-start}\label{algline:closure-end}
\item $R\gets H\setminus S$;
$\mathcal{P}\gets\operatorname{OverlapGroups}(W(S))$
\item $m(p)\gets\min\{i\mid E_i\in S,\ W_i\bowtie p\}$, $p\in\mathcal{P}$
\item \textbf{if} $\exists p\in\mathcal{P},E_j\in R:\ j>m(p)\land W_j\bowtie p$ \textbf{return} $\bot$ \label{algline:conflict}
\item $A\gets\operatorname{Freeze}(F,c,H,G,V,Z,S)$
\item $Z_t\gets T_S(\operatorname{Clone}(Z))$ \label{algline:restore}\label{algline:context}
\item \textbf{if} $\neg\operatorname{Audit}(Z_t,A)\lor\neg\operatorname{Fresh}(A)$ \textbf{return} $\bot$
\item $Z\gets T_S(Z)$
\item \textbf{return} $(Z,S,\operatorname{Audit}(Z,A))$
\end{enumerate}
\end{algorithm}

\textbf{Proposition 1 (file-scope rollback consistency).}
Under the assumptions above, an accepted recovery removes every call
reachable from $B$, preserves the retained history $R$, and satisfies
\[
  X^{+}|_F=X_c|_F,\qquad
  C^{+}=\operatorname{Project}(C,R).
\]
Filesystem state outside the restored groups is unchanged. Retained calls
have no dependency on the withdrawn scope in the covered dependency graph.

\emph{Proof.}
The reachability computation starts from every post-checkpoint mutation
of $F$. Each strict closure expansion adds a call, reaching the least fixed
point $S=\operatorname{Reach}_G(B)$. Hence no edge leaves $S$ for $R$.
If $G$ covers the true dependencies, every call depending on the reported
mutations is withdrawn. A retained call cannot consume a withdrawn file
version or result, since that dependency would place it in $S$.

For a restored group $p$, no selected mutation precedes $m(p)$.
The saved state $V_{m(p)}|_p$ therefore includes all earlier retained writes.
Line~\ref{algline:conflict} excludes later retained mutations of $p$;
restoring that saved state yields the group's state with the selected
mutations removed. The groups do not overlap, so their assignments commute.
Outside these groups, no selected call mutates the managed state, which
therefore stays unchanged. Together, these facts preserve the filesystem
state of retained calls in their original order. Every mutation of $F$
after $c$ belongs to $B$, so no such mutation survives and
$X^{+}|_F=X_c|_F$. Projection removes exactly the corresponding call/result
pairs and preserves those of $R$. The frozen audit checks these invariants
before the agent resumes.

\textbf{Corollary (idempotence of a fixed plan).}
Let $Z=(X,C,\operatorname{Active}(H))$ and let $T_S$ apply the frozen
saved versions, inactive marks, and record projection. Reassigning the same
versions and projecting onto $R$ twice leaves the managed state unchanged:
$T_S(T_S(Z))=T_S(Z)$. Recovery notices and audit counters are outside
this state equality; the API rejects stale plans instead of recomputing
their scope during application.

This proves consistency of the requested rollback, conditional on capture
coverage. It neither identifies an upstream mistake outside the reported
scope nor proves that the original task is solved. A semantically valid
checkpoint restores that validity for the reported files; subsequent task
completion is checked separately.

DeltaBox~\cite{deltabox} on Linux 6.8.0-147, using 4\,GiB Ext4 and
reflink-enabled XFS volumes.
Native Ext4 and XFS provide direct-update references.
Partial-update tests perform five non-truncating 4\,KiB edits to a
1\,MiB file, retaining the initial version and checkpointing after each
edit. Block-device writes and edit latency include \texttt{syncfs} but
exclude the subsequent checkpoint. The remaining tests use 100 target
files and overwrite ten seed files, all 4\,KiB, before each of 1, 10,
or 30 checkpoints. For \trycmd, checkpoint timing includes saving an
environment, exiting, and reentering a new view.
Workflow time covers setup, buffered writes, checkpoints, publication,
and cleanup. We report twenty timing runs per configuration. Resource
overhead is the difference in growth from initialization to just before
publication between ten paired runs with and without checkpoints.
Storage counts shared extents once; memory includes anonymous pages,
file cache, and kernel allocations across all worker processes.

Figure~\ref{fig:rq5-storage}(a--b) shows that XFS reduces the data
copied for partial updates. On Ext4, \system writes 1,102.44\,KiB per
edit because copy-up copies the original file; XFS reflink shares
unchanged extents, reducing writes to 12.71\,KiB. Synced edit latency
falls from 4.496 to 1.331\,ms. On XFS, OverlayFS and DeltaBox write
12.71 and 12.73\,KiB with similar edit latency. Thus, the user-space
controller preserves the data-sharing benefits of the backing filesystem.

Figure~\ref{fig:rq5-storage}(c--d) shows the benefit of retaining mount
references during checkpoint creation. Across the tested depths,
\system takes 0.58--0.67\,ms per checkpoint, a 4.20--13.66$\times$
speedup over OverlayFS. At thirty checkpoints, complete workflows take
95.22\,ms on Ext4 and 99.22\,ms on XFS, reducing time by 30.8\% and
30.5\% relative to OverlayFS, and by 79.8\% and 84.3\% relative to
BranchFS. The corresponding \trycmd workflows take 14.159 and
13.958\,s. DeltaBox has lower repeated-checkpoint costs, taking
0.546 and 0.504\,ms per checkpoint at this depth on Ext4 and XFS.

Figure~\ref{fig:rq5-storage}(e--f) shows the resource cost of this
optimization. At thirty checkpoints, \system uses 1,524\,KiB of extra
storage on Ext4 and 1,284\,KiB on XFS, just 4\,KiB more than OverlayFS
and DeltaBox for generation records. Extra memory is 2,760.4 and
2,499.2\,KiB, respectively, about 1\,MiB above those two systems
because retained mount references keep kernel metadata live.
Both storage and memory remain below the corresponding BranchFS and
\trycmd costs. The main tradeoff is therefore additional resident
memory for faster checkpoints, with little extra storage.

\section{Discussion}

\textbf{Object identity and reconstruction.}
OverlayFS \texttt{index=on} preserves session hard-link
visibility~\cite{overlayfs}. Object identifiers and resolved paths link
accesses in the dependency graph. For each affected group, reconstruction
restores entries from the nearest compatible checkpoint preceding its earliest
selected mutation while retaining independent changes.

\textbf{Tracing backends.}
Command strings can omit indirect reads, so \system uses \texttt{strace}.
System-call tracing has workload-dependent cost and is Linux-specific.
In a 12-step probe, \texttt{strace} and persistent eBPF capture the same reads
and negative lookups, taking 25.60 and 61.39 ms/step, respectively.

\textbf{Transaction state.}
Transaction state covers workspace filesystem effects and tool-call history.
Network effects need subsystem-specific compensation~\cite{sagas}; hidden
provider state needs service support.

\section{Related Work}

\textbf{Isolation and state restoration.}
\trycmd lets callers selectively apply or discard program effects; Sandlock
confines effects in a copy-on-write directory~\cite{try-osdi26,sandlock}.
YoloFS stages filesystem changes and supports travel to saved
checkpoints~\cite{yolofs}.
BranchFS provides nested branches with commit/abort~\cite{branchfs}.
Waypoint restores files and
processes~\cite{waypoint}; DeltaBox pairs DeltaFS layer switching with
DeltaCR process restoration~\cite{deltabox}. \system selects completed calls
to withdraw and combines compatible historical object versions with current
independent updates. Foundations
include transactional updates~\cite{valor,txfs}, crash-consistency
testing~\cite{crashmonkey}, and record/replay~\cite{revirt,rr}.

\textbf{Checkpoint decisions and agent continuation.}
Crab selects resources and overlaps checkpoint capture with execution;
RippleCP selects checkpoints to materialize~\cite{crab,ripplecp}.
AgentRewind restores environment/context checkpoints and retains lessons;
Rollback-Induced Reflection reuses lessons after environment
restoration~\cite{agentrewind,rir}. Planarian restores local and supported
remote state while retaining context~\cite{planarian}. LogAct recovers
interrupted operations through intention/result logs~\cite{logact}.

\textbf{Dependency-guided recovery.}
Taser and RETRO repair attack effects while preserving legitimate
work~\cite{taser,retro}; BackTracker explains intrusions~\cite{backtracker}.
Provenance systems record dependencies~\cite{pass,hifi,camflow}; BEEP
reduces excessive dependencies through execution partitioning~\cite{beep}.
hS schedules dependent subprocesses; Cordon validates composed effects
through result lineage before commit and discards transaction shadow state on
abort~\cite{hs-osdi26,cordon}. revGo rolls back and replays channel operations; AquaMend
compares action-graph recovery choices~\cite{revgo,aquamend}. \system uses
file and returned-value dependencies to select calls within and across turns,
preserving independent work within partially withdrawn turns.
Starting from user-reported files, one set guides object restoration and
call/result withdrawal, with an isolated residue audit before live changes.

\textbf{Agent memory and derived-state repair.}
Reflexion retains feedback; MemGPT manages information across context and memory
tiers~\cite{reflexion,memgpt}. MemoRepair repairs summaries, cached outputs,
and procedures through influence dependencies~\cite{memorepair}.
\system synchronizes retained call/result history with filesystem state.

\section{Conclusion}

An erroneous tool call can affect later calls through both files and reused
results. Given a user-specified file, \system withdraws its post-checkpoint
mutations and their joint file/result dependency closure. A residue audit
checks the resulting state before model continuation. The selected set guides both
object restoration and updates to agent context, preserving independent
calls within and across turns. Recovery can thus reconstruct a file state
absent from the saved checkpoints while the session remains speculative.

Across 400 fixed trajectories with three repetitions per policy, totaling
6,000 runs over five policies, \system removes all affected calls in its
1,200 runs while retaining all independent work; Crab and DeltaBox
discard 54.02\% and 56.90\% of valid work, respectively.
On matched successful task pairs, \system reduces token use relative to
DeltaBox by 17.55--23.45\% on SWE-Bench Lite and 25.39--44.69\% on
Terminal-Bench. Real-task breakdowns show lower agent-execution and
setup/replay costs relative to DeltaBox.
