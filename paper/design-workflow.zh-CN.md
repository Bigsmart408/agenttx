# 因果图驱动的选择性恢复：中文初稿

本稿衔接当前论文的动机分析，整理设计难点及第 4、5 节的中文表述，供讨论后再修改英文正文。

## 动机与设计的衔接

前面的观察表明，恢复的浪费来自回滚边界与依赖关系的不一致。工具调用按时间先后执行，但错误产生的影响可能跨越多个调用，也可能绕过中间的独立工作。只撤销某个可疑修改可能留下其派生结果；恢复整个时间后缀或分支，则会把有效工作一并删除。因而，缩短检查点间隔只能改变额外损失的大小，不能普遍表达所需的保留状态。

我们的设计以工具步骤之间的依赖图确定恢复范围。整个执行轨迹共享一份推测状态，运行时持续记录步骤产生和消费的效果；用户指出要回退的文件后，恢复流程选取该文件在参考 checkpoint 之后的全部修改，再沿文件和工具结果依赖确定需要共同撤销的步骤。最终恢复的是图所界定的效果子集，而不是某个时间点之后的全部工作。

## 设计难点

**第一，如何从不透明执行中发现恢复依赖。** Agent 使用 shell、编译器和测试程序完成工作，命令边界与参数不能可靠揭示内部读取了哪些状态。依赖还可能经过工具返回值传到后续请求，并不表现为文件读取。漏掉这些关系会保留已经失效的派生工作；仅凭执行先后添加关系，又会把独立步骤纳入恢复集合，重新产生时间回滚的浪费。因此，系统需要从实际观察到的文件行为和结果传递中建立恢复依赖图。

**第二，如何把不同名称上的效果关联到相应对象与版本。** 同一对象可能经由不同路径访问，同一路径也可能在重命名、替换或多次写入后指向不同状态。仅比较路径字符串可能漏掉别名间的依赖，而把同名对象的所有历史状态混为一体，也可能扩大恢复范围或选错恢复版本。依赖图中的连接和历史状态的选择必须使用一致的对象关系，才能回答一次访问消费了什么状态，以及选中效果被移除后应恢复成什么状态。

**第三，如何将依赖子图落实为工作区与上下文一致的非前缀状态。** 选出失效步骤只确定了逻辑范围，还没有生成可继续执行的状态。需要移除的修改与保留的工作可能在时间上交错，同一对象又可能被反复覆盖，因此恢复整个 checkpoint会删除有效进展，简单删除最新文件也无法恢复正确历史版本。同时，若工作区已经撤销某个结果，而 Agent 的后续输入仍包含该结果，恢复后的执行仍可能沿用失效依据。系统必须按同一恢复集合重建受影响对象和 Agent 可见历史，并拒绝无法安全保留的冲突状态。

## 4 基于因果依赖的选择性恢复

### 4.1 将恢复范围从执行边界中分离

动机分析表明，按轮次、检查点或分支回滚会丢弃边界内的独立工作。这种浪费来自恢复机制只能选择时间区间或执行单元，而实际失效范围由步骤间的依赖决定。因此，AgentTX 将完整执行轨迹作为推测单元，将依赖图中需要失效的子图作为恢复单元。

考虑引言中的交错执行：步骤 $s_0$ 修改格式化程序，$s_1$ 使用它生成报告，$s_2$ 编辑独立文档，$s_3$ 检查报告并发现错误。如果一个恢复方案选择撤销 $s_0$，仅撤销该步会留下依赖它的报告；恢复到它之前的检查点又会丢弃文档编辑。依赖关系则允许将 $s_0$、$s_1$ 和 $s_3$ 作为一个恢复集合，同时保留 $s_2$。

为表达这种分离，我们将一条轨迹建模为 Agent Effect Transaction（AET）。执行不断追加步骤及其效果；收到用户文件提示后，系统由指定文件的修改及依赖形成恢复集合，再检查并重建剩余状态。其关键不是把检查点切得更细，而是让恢复范围能够跨越时间上的间隔，排除其中不受影响的工作。

### 4.2 用可观察效果构建恢复依赖图

恢复依赖图以工具步骤为节点，以需要共同维护有效性的关系为有向边。如果后一步读取了前一步产生或修改的对象，前一步失效就会影响后一步的结果。图还记录覆盖同一对象的修改、删除以及对不存在状态的观察所引入的恢复约束。这些关系来自执行效果，而非命令文本或两个步骤在时间上的相邻关系。

对象关联决定了依赖边是否可靠。不同路径可能指向同一对象，同一路径也可能在替换后对应不同对象；只比较路径名称会遗漏别名访问，也可能混淆历史版本。AET 因而将效果与可建立关联的对象及其历史状态联系起来。这样的关联既支持建图，也为后续选择恢复版本提供依据。

依赖还可能通过 Agent 可见结果传播。一个工具返回值被后续请求使用时，即使没有中间文件，也可能影响后续工作。AET 将工具请求和结果与步骤关联，并把可检测的结果值传递纳入恢复依赖。文件与消息关系共同构成一个可分叉、汇合的图；文中以因果链描述失效传播过程，不要求轨迹具有线性依赖结构。

### 4.3 从文件提示计算统一失效集合

用户指出需要回退的文件，不提供错误 step。参考 checkpoint 表示某次调用结束后的状态，默认使用已提交边界。运行时对文件路径和已知别名归一化，选取该 checkpoint 之后对文件的全部修改作为根集合 B。

从 B 出发，反复沿文件和工具结果依赖扩展，直到集合不再增加，得到 S。恢复撤销该文件的一段修改历史及其派生工作，不声称其中某一步一定是语义错误的根因。在格式化器、报告和文档的例子中，用户指定格式化器文件后，其修改以及依赖它生成的报告进入 S；独立文档保留。

运行时在恢复前冻结依赖图、文件版本及有效调用与结果标识，在隔离分支应用 S 后检查命令、文件效果和上下文残留。任务测试不参与集合选择；未知文件、缺失历史、恢复冲突或残留检查失败都会使恢复结果不确定。

### 4.4 将失效子图落实为一致的幸存状态

从图中选出步骤，还不足以得到可继续使用的工作区。同一对象可能经历多次写入或删除，简单删除当前文件可能同时破坏更早的有效版本。恢复需要为每个受影响对象选择其最早失效修改之前的历史状态，并检查这一替换是否与保留修改发生冲突。运行时拒绝无法安全处理的重叠。

工作区与 Agent 可见上下文必须使用同一个失效集合。只恢复文件而继续保留失效工具结果，会使 Agent 在下一轮请求中再次依据过期状态行动。AET 因而移除失效步骤对应的调用与结果，保留独立步骤的有效消息，并说明哪些工作仍然存在。在例子中，文档及其有效记录一起保留，无效报告及相关结果一起失效。

成功恢复保持两项性质：选中子图的修改不再可见，不冲突的保留效果继续可见；下一次模型请求与该工作区表达相同的幸存步骤集合。Agent 随后在保留进展上继续修复和验证。

## 5 AgentTX 实现：将因果恢复集合落实为状态

AgentTX 在 Linux 上实现前述恢复模型。运行时在持续执行中积累依赖证据和对象历史；收到用户文件提示后，计算相应修改的依赖闭包，并在隔离分支中检查恢复状态，再以同一集合恢复工作区和 Agent 可见上下文。恢复范围由依赖关系界定，使与错误交错的独立工作不必随时间后缀或整个分支一起丢弃。

### 5.1 持续执行与依赖记录

AgentTX 为一次会话建立共享推测工作区，并让后续工具调用复用它。我们在 OverlayFS 之上扩展恢复运行时，将项目基线与会话内修改组合成共享执行视图，使后续调用能够消费早先结果，而不直接修改项目基线。调用返回只增加轨迹中的一个步骤，不结束整个推测环境。

每次调用前，版本存储保留后续恢复所需的历史状态。调用期间，系统调用跟踪捕获支持范围内的读取和失败查找；调用结束后，工作区上层的状态差异提供写入和删除效果。运行时将这些证据关联到当前步骤，再根据与先前效果的关系建立依赖，而不从命令文本猜测读写集合。

原生工具调用的请求与结果也绑定到步骤。当后续请求复制了先前结果中可识别的值时，对话日志记录相应依赖。因此，文件状态和工具返回值都是失效传播的来源。

### 5.2 关联对象、依赖与历史版本

依赖图需要知道两个访问是否涉及同一对象，版本恢复也需要知道应该替换哪个对象。AgentTX 将路径层次关系、支持的符号链接解析结果和经过验证的硬链接关系纳入效果规范化，避免同一对象以不同名字绕过依赖判断。重命名以旧名称删除和新名称创建参与记录。

对象的名称关联与历史状态共同支撑恢复。前者将相关访问连接起来，后者保存对象在各步骤之前的内容和必要元数据。实现利用上层 checkpoint及不可变内容存储保留这些版本，使恢复可以直接取回目标状态。重建需要尚未确认的对象关系时，运行时拒绝操作。

### 5.3 文件提示入口

控制器接收需要回退的文件和参考 checkpoint。它选出指定文件在该边界之后的所有活动修改，不搜索错误 step，也不通过遍历候选直到任务测试通过来决定撤销范围。对照策略继续接收具体 step；Crab 还接收受影响 turns。

### 5.4 扩展依赖集合并检查恢复状态

运行时交替扩展文件和工具结果依赖，得到包含全部文件修改根的最小闭包 S。一次结果复用可能引入新的文件写入者，因此需要反复扩展到固定点。

审计在恢复前保存参考文件状态、历史版本和有效记录标识。在隔离副本应用 S 后，它检查应撤销命令及结果是否仍然可见、是否存在从已撤销命令到保留命令的依赖、指定文件是否回到 checkpoint，以及保留文件和 lower 是否改变。

隔离审计通过后，控制器检查实时历史签名，将同一冻结方案应用到实时状态，并在模型续跑前重新审计。审计证明的是回滚状态与指定范围的一致性；原任务是否解出由后续任务测试单独判断。依赖捕获完整性仍是前提，需要独立工作流真值检查，不能由同一张依赖图自证。

### 5.5 按恢复集合重建工作区与上下文

确定失效步骤后，AgentTX 收集它们写入或删除的对象，并检查每组目标在最早选中修改之后是否还有保留写入；此前的有效写入可以通过保存版本保留。检查不通过时，运行时拒绝选择性恢复。检查通过后，对每组受影响路径选择最早失效修改之前的历史状态，恢复相应对象，保留其余工作区状态。这一过程使用历史版本，不重新执行产生保留结果的命令，也不把整个工作区恢复到某个旧时刻。

工作区恢复完成后，运行时更新失效步骤的状态，并用同一集合使对应工具请求、结果和过期恢复消息失效。文件提示入口再次审计实际工作区和有效记录，并将结果交回控制流程。原生 Agent 的下一次请求由有效消息及保留状态通知组成；不能改写内部历史的黑盒 Agent 则通过保留效果清单接收恢复状态。Agent 随后在仍然有效的进展上继续编辑和验证。

### 5.6 执行与历史维护开销

持久 worker 复用执行环境，增量历史只更新变化路径，内容寻址存储复用相同文件内容。这些机制降低连续记录与恢复的成本，不改变图所确定的失效集合。

### 正确性与幂等性

在依赖覆盖完整、历史版本准确且没有未跟踪写入的前提下，闭包 S 清除指定文件修改的所有后继。每组受影响路径恢复到其最早选中修改之前的状态，保留此前的有效写入；上下文投影删除同一集合的调用与结果。由此，指定文件回到参考 checkpoint，独立状态与记录保留。对固定 S 重复赋予相同版本、失效标记和记录投影，结果不变。这个幂等性结论针对冻结的状态变换，API 仍拒绝应用过期方案。
