# 5 Lancet 实现：将因果恢复集合落实为状态

Lancet 在 Linux 上实现前述恢复模型。运行时在持续执行中积累依赖证据和对象历史；观察到失败后，生成并检验候选恢复方案，再以通过检查的失效集合恢复工作区和 Agent 可见上下文。恢复范围由依赖关系界定，使与错误交错的独立工作不必随时间后缀或整个分支一起丢弃。

## 5.1 持续执行与依赖记录

Lancet 为一次会话建立共享推测工作区，并让后续工具调用复用它。我们通过 `try` 和 OverlayFS 将项目基线与会话内修改组合成执行视图，使后续调用能够消费早先结果，而不直接修改项目基线。调用返回只增加轨迹中的一个步骤，不结束整个推测环境。

每次调用前，版本存储保留后续恢复所需的历史状态。调用期间，系统调用跟踪捕获支持范围内的读取和失败查找；调用结束后，工作区上层的状态差异提供写入和删除效果。运行时将这些证据关联到当前步骤，再根据与先前效果的关系建立依赖，而不从命令文本猜测读写集合。

原生工具调用的请求与结果也绑定到步骤。当后续请求复制了先前结果中可识别的值时，对话日志记录相应依赖。因此，文件状态和工具返回值都是失效传播的来源。

## 5.2 关联对象、依赖与历史版本

依赖图需要知道两个访问是否涉及同一对象，版本恢复也需要知道应该替换哪个对象。Lancet 将路径层次关系、支持的符号链接解析结果和经过验证的硬链接关系纳入效果规范化，避免同一对象以不同名字绕过依赖判断。重命名以旧名称删除和新名称创建参与记录。

对象的名称关联与历史状态共同支撑恢复。前者将相关访问连接起来，后者保存对象在各步骤之前的内容和必要元数据。实现利用上层快照及不可变内容存储保留这些版本，使恢复可以直接取回目标状态。重建需要尚未确认的对象关系时，运行时拒绝操作。

## 5.3 独立的候选定位模块

可信检查失败并请求恢复后，控制器调用定位模块，沿该检查的依赖追溯先前修改，并结合诊断信息生成候选起点。依赖距离和诊断引用确定候选方案的尝试顺序。

定位模块缩小尝试范围，恢复模块为每个候选扩展需要共同撤销的依赖子图，再检验方案。两者共同将失败观察转化为可执行的恢复集合。

## 5.4 扩展因果集合并检验恢复方案

对于每个候选或候选组合，运行时先沿文件依赖扩展后继，再沿消息依赖继续扩展，并反复执行两种扩展，直到集合不再增加。消息依赖可能引入新的文件写入者，因此不能只计算文件闭包后再删除消息。候选起点和这些后继共同组成一次试验的失效集合。

Lancet 在隔离副本中应用这一集合并重新运行同一检查，而不直接改动实时工作区。系统在探测预算内选择通过检查且丢失工作较少的方案；没有得到通过的因果方案时，该路径报告结果不确定并保持实时视图。

依赖图在这一过程中有两个用途：反向追溯候选回答从哪里尝试恢复，正向扩展后继回答必须连带撤销什么。对于格式化器、报告和独立文档的例子，候选方案需要把格式化器的相关修改与依赖报告一起考虑；独立文档不因执行时间较晚而被纳入。这种集合选择直接减少由固定恢复边界引入的额外损失。

## 5.5 按恢复集合重建工作区与上下文

确定失效步骤后，Lancet 收集它们写入或删除的对象，并检查这些目标是否与保留步骤的写入存在无法支持的重叠。检查不通过时，运行时拒绝选择性恢复。检查通过后，对每组受影响路径选择最早失效修改之前的历史状态，恢复相应对象，保留其余工作区状态。这一过程使用历史版本，不重新执行产生保留结果的命令，也不把整个工作区恢复到某个旧时刻。

工作区恢复完成后，运行时更新失效步骤的状态，并用同一集合使对应工具请求、结果和过期恢复消息失效。验证器驱动的入口再次检查实际工作区，并将复验结果交回控制流程。原生 Agent 的下一次请求由有效消息及保留状态通知组成；不能改写内部历史的黑盒 Agent 则通过保留效果清单接收恢复状态。Agent 随后在仍然有效的进展上继续编辑和验证。

## 5.6 执行与历史维护开销

持久 worker 复用执行环境，增量快照只更新变化路径，内容寻址存储复用相同文件内容。这些机制降低连续记录与恢复的成本，不改变图所确定的失效集合。
