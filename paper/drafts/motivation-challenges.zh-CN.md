# 从动机到设计：中文草稿

## 动机与设计的衔接

前面的观察表明，恢复的浪费来自回滚边界与依赖关系的不一致。工具调用按时间先后执行，但错误产生的影响可能跨越多个调用，也可能绕过中间的独立工作。只撤销某个可疑修改可能留下其派生结果；恢复整个时间后缀或分支，则会把有效工作一并删除。因而，缩短检查点间隔只能改变额外损失的大小，不能普遍表达所需的保留状态。

我们的设计以工具步骤之间的依赖图确定恢复范围。整个执行轨迹共享一份推测状态，运行时持续记录步骤产生和消费的效果；出现失败后，恢复流程利用这些证据提出候选方案，并沿依赖关系确定需要共同失效的步骤。最终恢复的是图所界定的效果子集，而不是某个时间点之后的全部工作。

## 设计难点

**第一，如何从不透明执行中发现恢复依赖。** Agent 使用 shell、编译器和测试程序完成工作，命令边界与参数不能可靠揭示内部读取了哪些状态。依赖还可能经过工具返回值传到后续请求，并不表现为文件读取。漏掉这些关系会保留已经失效的派生工作；仅凭执行先后添加关系，又会把独立步骤纳入恢复集合，重新产生时间回滚的浪费。因此，系统需要从实际观察到的文件行为和结果传递中建立恢复依赖图。

**第二，如何把不同名称上的效果关联到相应对象与版本。** 同一对象可能经由不同路径访问，同一路径也可能在重命名、替换或多次写入后指向不同状态。仅比较路径字符串可能漏掉别名间的依赖，而把同名对象的所有历史状态混为一体，也可能扩大恢复范围或选错恢复版本。依赖图中的连接和历史状态的选择必须使用一致的对象关系，才能回答一次访问消费了什么状态，以及选中效果被移除后应恢复成什么状态。

**第三，如何将依赖子图落实为工作区与上下文一致的非前缀状态。** 选出失效步骤只确定了逻辑范围，还没有生成可继续执行的状态。需要移除的修改与保留的工作可能在时间上交错，同一对象又可能被反复覆盖，因此恢复整个快照会删除有效进展，简单删除最新文件也无法恢复正确历史版本。同时，若工作区已经撤销某个结果，而 Agent 的后续输入仍包含该结果，恢复后的执行仍可能沿用失效依据。系统必须按同一恢复集合重建受影响对象和 Agent 可见历史，并拒绝无法安全保留的冲突状态。
