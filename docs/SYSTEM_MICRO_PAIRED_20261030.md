## 实验主线

失败观测 → 定位候选 → 依赖闭包 → 文件与可见上下文恢复 → 模型继续修复 → 正确性与实际成本。

两个策略看到相同案例、故障计划、任务、模型、时限与完整恢复上下文。AgentTX 使用捕获的依赖与隔离验证定位；时间后缀基线用相同公共产物合约寻找首个失败操作，再恢复后缀。基线的检查调用与耗时计入结果。生成器真值只用于注入、事后定位/闭包评分和独立最终验证，不直接交给定位器。

Ideal 不另跑模型组；其正确集合由生成器计算。原有轮次、整分支、不回滚及五后端结果保留各自范围。

- 最多 8 个并行单元；每单元模型时限 3600 秒，无 model-call/step cap。
- 每单元 API token 预算 8,000,000。每次调用前为输入序列化字节与额外 framing 预留额度，并限制本次最大 completion；用实际响应 usage 累计费用。超预算、失败请求或未知用量均留档，不能填零；出现预算越界或费用不全时停止新增派发并核查。
- 当前定位探测预算在执行前固定为 `2 × operation_count + 8`，不会按观察到的准确率或节省放宽。
- 不按任务成败或收益方向重跑。运行时/环境异常停止新增，保留在途结果与原始费用。
- 三重复按同一 case/repeat 成对；成功情况保留全部分母，成本比较使用双方成功且用量完整的配对。后续区间按 case 重采样，不能把三重复当成三个独立任务。

一次运行同时记录 RQ1 与 RQ3：注入步骤匹配、候选排序、实际探测次数、定位时间、无效效果移除、独立工作保留、选择精度、workspace/context 一致性、命令审计、最终任务验证、实际 API prompt/completion/total tokens、工具调用与各阶段耗时。

## 纯读命令与候选过滤

用户提出过滤 `ls` 等不改文件的命令。当前定位器已只从带 WRITE/DELETE 效果的活跃祖先中产生候选，纯读命令不会成为文件系统回滚起点。判断依据是实际捕获效果，不能按命令名白名单忽略脚本、重定向或子进程写入。

纯读结果仍可能形成依赖：例如 `ls` 的结果决定后续创建/修改行为，或观察到缺失路径后采取动作。因此，保留其读取/negative lookup 和消息关联；不能为减图而删除这些关系。写入节点及其版本属于恢复对象，观察记录则支持依赖与上下文失效。压缩观察记录是后续可评估的优化，当前不改变冻结批次的语义。

可进一步采用以下图压缩流程，作为后续实现方案，不能当作本批已实现的功能：

1. 执行后按捕获到的实际效果分类。包含 WRITE/DELETE 的调用保留为文件状态变化节点；无此类效果的调用只保留观察及消息记录，不创建独立的文件恢复节点。分类对象是整个被包裹的调用，不能因外层命令叫 `ls` 就跳过跟踪。
2. 对纯读观察，记录它依赖的文件版本或目录状态，以及使用其结果的后续调用。例：`创建文件 A → ls 观察到 A → 后续调用据此写入 B`。压缩后可在写节点图中保留 `创建 A → 写入 B`，同时保留 `ls` 输出到上下文记录的关联。
3. 恢复时沿压缩后的因果关系确定失效写入，再通过观察关联使对应输出和受其影响的上下文失效。原先经过观察节点的可达关系必须保留；尚不能确认的依赖继续保守保留。

该方案的难点是保留观察所传递的因果关系，而非识别 `ls` 这个命令名。它可能减少写节点图的规模和遍历成本；当前定位器已过滤纯读候选，不能把同一效果重复计为减少定位探测。验证压缩应比较相同轨迹在压缩前后的写入失效集与上下文失效集，再测量图大小和构建/遍历成本。

本批受控 manifest 的每条原始操作都写一个产物，因而纯读过滤不改变这 400 case 的原始写候选数量。预检中较长案例主要耗时来自候选探测；现有实现只有候选数量超过探测预算时才优先进行分组搜索。该成本应如实计入 RQ3，不能中途换策略后拼接结果。
