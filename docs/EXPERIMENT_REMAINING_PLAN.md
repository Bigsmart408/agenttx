## 4. 每一组究竟要验证什么

### 完整系统微基准

策略：`clean_recovery`、`crash_no_rollback`、`turn_checkpoint`、`temporal_checkpoint`、`whole_branch_abort`、`causal`、`ideal_oracle`。

全部使用原注册 400 manifest，不改依赖图、操作顺序、错误位置或精确保留集。oracle 从生成器注册真值取得完整 invalid set；远程注入器的三步骤真值只是特定注入轨迹，必须扩展到所有 manifest 和多根情况。causal 只能根据可观察证据定位，不得共享 oracle 集合。

逐单元输出官方/任务成功、invalid removal、valid retention、workspace/context agreement、main/replay/total tokens、工具调用、定位/恢复/重放/验收/端到端时间。配对成功单元的效率与所有尝试的成功率、成本同时报告；失败的低 token 不能算节省。

### 正式真实任务

五策略为 `clean_recovery`（无故障恢复上下文对照）、`crash_no_rollback`（崩溃后不回滚）、`temporal_checkpoint`（时间检查点回滚）、`whole_branch_abort`（整分支放弃）和 `causal`（AgentTX 因果恢复）；每任务策略一次，两种 harness 分别统计。只在真实可区分多轮边界的 runner 上增加 turn checkpoint，并单列额外规模。

冻结任务 catalog 和官方 verifier；TB 的两种 agent 都在官方任务镜像运行。SWE-agent 不从 synthetic workload 的 turns 隐式继承 model-call/step cap；若加 cap，Codex 也须匹配并记录。故障数量、位置、预算和超时一致，clean 对照无故障。

统一 compact/full 和模板规则，另记策略必需 payload tokens；如果研究提示词长短，把它作为独立消融。每组都记录完整模型用量（含重放），基础设施失败单列，不将超时/任务失败悄悄抹掉。分别报告 SWE、TB、各 harness，再考虑汇总；成功率使用同任务配对分析，成本以任务为单位计算差值和不确定性区间。

### Breakdown

| 配置 | 要验证的变化 |
| --- | --- |
| Full | 参考；符合冻结协议的主实验记录可复用 |
| No READ/NEGATIVE | 是否漏掉依赖后继 |
| Path-only identity | 别名/对象身份信息的必要性 |
| Temporal history only | 交错有效版本能否保留 |
| Workspace-only rollback | 旧工具结果是否与文件状态冲突 |
| One-shot worker | 语义相同前提下的每步骤/启动开销 |
| Full context handoff | 与 compact 的提示词及重放成本 |

每配置覆盖全部 400 manifest；7 配置一遍为 2800 配置单元，若统一采用主实验三重复则 8400。重复次数在执行前冻结，Full 满足同协议时复用，不重复计为新增实验。400 集合中未覆盖的 alias 等语义不能靠消融凭空证明，须在语义矩阵补齐。前四项主要解释正确性/保留效果，后两项解释工程成本；不把错误的结果当作更快的优化。

### 正确性与恢复中断

语义覆盖：读/写/删除、negative lookup→create、同路径多版本、目录祖先、rename、symlink、受支持 hardlink、fd-relative、多错误根、重复回滚、reload、未知身份 fail-closed。每例验证选中效果删除、独立效果保留、无效消息删除、保留消息与文件对应同一活动集合。

**重复请求验收有一处需要明确：** `agent.md` 当前写“第二次相同恢复为 no-op”，实现则对已回滚显式根返回 ValueError。远程证明只证明完整成功后的状态不再改变。需要选择并冻结“重复请求可拒绝但状态不变”的契约，或实现按 request ID 成功返回同一结果；不能把异常拒绝写成成功空操作，更不能由此推导中断重放安全。

五个 SIGKILL 点：计划持久化后/重建前；新 upper generation 建好/激活前；工作区切换后/context 前；context 后/元数据持久化前；持久化后/回复前。每点至少 20 次，重新加载同一 session 并续恢复，只接受完整 pre 或完整 post 的工作区与上下文对。已有 `test_midcrash_inject.py` 测的是注入位置，不替代这 100 次恢复中断实验。按规范完整矩阵位于后段；P0 提前做低成本预检以尽早暴露问题。

### 六类开销

覆盖命令类型/trace 体积，仓库大小/改动字节/轨迹长度，step 数/RSS，闭包大小/路径数/alias 组/根数，full/compact context，startup/teardown/reload/worker fallback。保存绝对毫秒、字节和 RSS；有足够重复时报告均值及 p50/p95/p99，少量样本不包装成稳定尾延迟。

## 5. 冻结与结果验收

每个新批次保存代码 commit + dirty diff hash、依赖锁定、模型/推理配置、提示词文本和 hash、官方镜像 ID/Python、任务版本、manifest hash、故障 seed/schedule、timeout/count cap、结果 schema、用量来源与排除理由。语义变更新建目录，不 skip 任意已有文件就当完成。

预先定义环境重试规则、最大次数和终止结果保留方式，保留所有尝试。汇总前检查预期键无漏项/重复、同 case 输入与故障一致、结果可从原始行重建；对环境错误单列数量，同时给出总计划/总尝试/任务有效分母。恢复片段、部分 CSV、未知验收元数据不进入正式结果。

最终主结论需要完整原始证据支持：选择性恢复正确性、真实任务总 token/时间收益、各部件必要性、支持语义边界和中断恢复安全。当前前两类受控证据最强，真实成本与 crash-safe 保证仍需上述实验补足。
