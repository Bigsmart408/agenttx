# 进程状态后续生命周期：三组固定轨迹对照

用户要求补充上一轮遗漏的两个问题：与不发生错误的执行比较，以及保留的无用进程状态
在继续执行后是否释放、何时释放、是否影响结果。原有两组单次查询实验保留，新附录使用
独立注册的三组对照。

## 实际执行的内容

每个案例运行两个独立应用服务，在一个服务中消费输入文件，在另一个服务中保留独立
有效状态。每次先预热有效缓存，再写入并消费输入文件，生成一个依赖输出，并写入一个
独立文件。两组恢复实验注入同一错误，使用完全相同的文件系统与上下文因果回滚集合。

三组分别为：

1. **全部保留**：恢复文件系统和上下文，保留两个应用进程及其内存。
2. **全部清空**：同样恢复文件系统和上下文，然后终止两个应用进程并启动无历史内存的新实例。
3. **Clean**：同一工作负载始终使用正确输入，不注入错误，不回滚，不清空进程。

公共后续轨迹先用正确文件重新生成依赖输出，使三组文件内容一致，再执行 16 条服务请求。
应用在需要时按正常逻辑重建缺失的有效缓存。请求中没有垃圾回收、回滚式内存清理或
专门驱逐错误条目的指令。

## 生命周期覆盖与配置

| 类型 | 后续正常行为 |
|---|---|
| 请求内临时缓冲区 | 请求返回时对象不再被引用 |
| 查询时刷新 | 新查询用当前文件内容替换旧缓存 |
| LRU 缓存 | 新键进入，按常规 LRU 规则淘汰旧键 |
| 到期缓存 | 普通请求触发过期检查并清理 |
| 有限作业 | 工作处理完毕后进程正常退出，下一个作业启动新进程 |
| 不再访问的持久缓存 | 不访问旧键，也不主动淘汰 |
| 再次访问的持久缓存 | 继续使用缓存值 |

7 类 × 10 个输入 × 3 次重复 × 3 组 = **210 组三组对照、630 次执行**。
每个输入创建 32–320 个 payload，每个 payload 含 4 KiB 数据。
LRU 容量等于初始条目数，每条后续命令插入 8 个新键。
到期时间为 0.1–1 秒；有限作业处理 4–13 次请求后正常退出。
三组顺序按输入和重复轮转，两个服务在所有组中使用同一实现。
全过程为固定脚本，不调用 agent、模型或模型 API。

## 如何测量

- 用弱引用及 finalization callback 观测对象，不用强引用把待测对象人为留住。
- 进程正常退出通过 PID、返回码和最后一次响应共同验证。
- “自行释放”包括作用域结束、正常覆盖、LRU 淘汰、按请求过期清理和作业自然结束。
- “全部清空”以及实验结束后的强制清理不计入自行释放。
- 同时记录全部错误对象和回滚时仍驻留对象两个分母。
- 对每一条后续请求比较 clean 组结果；单独记录有效缓存保留、后续重建条目数。
- 对象释放指应用不再持有该 payload，不等同于 Python 分配器把物理内存归还操作系统。

这是一组具有明确生命周期配置的受控实验。总体比例描述这组配置，不作为 SWE-Bench/TB
真实进程状态的出现率或自然回收率。

## 已核验结果与结论

正式执行 **630/630 完成并通过独立核验**，模型调用和模型 API 请求均为 0。
完整逐次结果与证据哈希保存在 `review/process-lifecycle-fixed-20261110-r1/runs.csv`
及 `audit.json`；附录改用本轮三组结果。

| 组别 | 16 条后续结果全部与 clean 一致 | 恢复后立即保留的有效缓存 | 相对 clean 多做的缓存构建 |
|---|---:|---:|---:|
| 全部保留 | 180/210（85.71%） | 100% | 0% |
| 全部清空 | 210/210 | 0% | +100% |
| Clean | 210/210 | 100% | 0% |

保留组生成 36,960 个错误 payload 对象，其中 5,280 个请求内临时对象在回滚前就已释放。
回滚时剩余 31,680 个，继续 16 条命令后自然释放 19,104 个，比例 **60.30%**。
计入回滚前释放的对象，总释放 24,384/36,960，即 **65.97%**。

| 生命周期 | 回滚前已释放 | 第 4 条后累计释放 | 第 16 条后累计释放 | 保留组正确轨迹 |
|---|---:|---:|---:|---:|
| 请求内缓冲区 | 100% | 100% | 100% | 30/30 |
| 查询时刷新 | 0% | 100% | 100% | 30/30 |
| LRU | 0% | 18.18% | 61.82% | 30/30 |
| 到期清理 | 0% | 100% | 100% | 30/30 |
| 有限作业退出 | 0% | 1.82% | 100% | 30/30 |
| 不再访问的持久缓存 | 0% | 0% | 0% | 30/30 |
| 再次访问的持久缓存 | 0% | 0% | 0% | 0/30 |

无用的持久缓存可能一直驻留，但在这段后续轨迹中不再使用时，结果仍与 clean 一致。
再次使用错误缓存时，30 条轨迹各产生 16 个错误响应，共 480 个。
有限作业的 30 个初始 worker 全部自然退出；这是进程退出的观测，与对象释放分母分开。

清空后有效缓存并非一直缺失：正常请求会重新构建。三组结束时有效缓存内容均正确，
但清空组一共构建 137,280 个有效条目，保留与 clean 各构建 68,640 个。因此清空组多做
100% 的缓存构建，保留组无额外构建。

核心结论：部分残留会随正常生命周期消失，未再使用的残留也可以不影响后续结果；
持久残留被再次读取时才会继续传播错误。选择性进程恢复需要识别这些使用关系，
不能把全量清空等同于既消除错误又保留进展。

这组实验没有证明全量保留在所有情况下均正确：再次读取持久错误缓存的 30 条轨迹仍失败。
