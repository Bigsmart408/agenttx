# 实验目的、现有结果与证据关系

更新时间：2026 年 11 月 1 日。补充对照的进度快照为北京时间 16:36；已完成实验的结果与在途结果分开记录。

## 实验主线

执行边界会误删独立工作 → 依赖图确定真正受影响的集合 → 同步恢复文件与上下文 → 减少 Agent 重新修复的成本。

目前证据最扎实的是独立工作保留与修复 token 成本下降。成功率和完整流程耗时的优势依赖具体场景；高依赖情况下，候选验证开销可能抵消保留工作的收益。

## 1. Motivation：为什么现有回滚边界会浪费？

### 目的与设计

用相同的 400 个案例比较不恢复、只撤销根因、按轮恢复、时间后缀恢复、整分支恢复和理想恢复集合。向粗粒度策略提供准确的故障位置，按轮策略还获得受影响轮次，用来单独检验恢复粒度的表达能力。

这里的 oracle 辅助只服务于动机实验：即使把定位条件给得足够有利，现有边界能否保留独立工作？它不代表 AgentTX 在实际恢复时预先知道根因。

400 个案例由 100 个执行长度案例、90 个故障位置案例、210 个依赖案例组成。另通过 Try、BranchFS、YoloFS、Waypoint 的原生操作恢复同一批输入，检验实际后端能够表达的恢复状态。

### 现有结果

- 按轮恢复平均丢弃 **54.02%** 的有效工作；时间后缀丢弃 **56.90%**；整分支丢弃 **100%**。
- 理想恢复集合不丢弃有效工作；**390/400 个案例（97.5%）**的理想存活状态无法用一个时间前缀表示。
- 不恢复不移除任何受影响步骤；只撤销根因平均仅移除 **17.03%** 的受影响步骤，说明还需要处理依赖后继。
- 原生 YoloFS 和 Waypoint 平均各丢弃 **65.89%** 的有效工作；Try 与 BranchFS 的原生 discard/abort 丢弃完整投机单元。这些结果对应本实验使用的包装与恢复单元。
- 固定四个受影响操作，将分支从一轮增加到十轮，时间后缀额外丢弃的有效操作从 **8 个增至 116 个**；整分支从 **12 个增至 156 个**。

### 能支撑的结论

恢复边界造成的浪费在定位准确时仍然存在。细化到单步记录后，若仍然按时间后缀恢复，仍会删除因果链之外的独立工作。需要用依赖关系表达恢复集合。

这里的 token weight 是确定性的工作量归因，不是实际模型 API 用量。原生后端比较测量恢复状态与粒度，不等同于使用各后端运行完整 Agent 的模型成本比较。

## 2. 原生轨迹分析：真实 Agent 有没有这种结构？

### 目的与设计

沿用原生轨迹分析的文件访问口径，重新盘点现有 Clean 采集记录，替换原来的 189 条 SWE / 54 条 TB 中途快照。把有后续步骤的 workspace 写入或删除步骤视为假想故障根，按实际记录的文件访问构建最近前序写入依赖图，比较根的后继闭包与时间后缀。

每个任务选一条记录：优先正式采集导出，缺项才按固定顺序补入相同 SWE-agent 配置的预检或环境修复采集。选取不依据任务成败、轨迹长度或保留机会。完整但任务失败的轨迹、零机会任务与假想根均计入分母；截断轨迹单独汇总。

### 数据覆盖

本次使用的是专门采集逐步文件访问的原生 Clean 数据，其当前覆盖如下。

| 覆盖状态 | SWE-Bench | Terminal-Bench |
| --- | ---: | ---: |
| 基准任务总数 | 300 | 241 |
| 可分析的兼容文件访问轨迹 | 285 | 212 |
| 完整轨迹，正文与图使用的分母 | **258** | **123** |
| 截断轨迹，单独汇总 | 27 | 89 |
| 导出损坏 | 0 | 2 |
| 缺少兼容文件访问记录 | 15 | 27 |

15 个 SWE 缺项均有镜像内容校验失败记录。TB 的缺项原因与损坏文件逐条列在审计清单中。没有修改原始文件，也没有将缺项当作零机会任务。

Clean 的完整模型对话轨迹确实另有保留，包含命令、观察和轮次。后续端到端实验保留的对话不包含这次依赖统计所需的逐步实际文件访问；TB 的保留清单还明确记录了详细 ledger 已清理。此次更新使用全部可用、配置一致的专门访问采集，而没有从命令字符串推断 syscall 依赖。300 / 241 是基准任务规模，完整访问轨迹的统计分母为 258 / 123。

## 3. 400-case 完整系统实验：少回滚能否转化为实际收益？

### 目的与设计

沿完整流程测量：执行原始轨迹 → 观察检查失败 → 发现恢复计划 → 恢复文件与可见历史 → Agent 继续修复 → 最终验收。

AgentTX 与时间后缀回滚各运行 **400 案例 × 3 次**，共 **2400 次**。双方采用 SWE-agent、GPT-5.6 Luna、maximum reasoning、full context、相同输入与操作接口。根因由恢复流程发现，生成器真值用于故障注入和事后评分。

每次模型执行限时 3600 s，实际 API-token 预算 800 万。成功要求最终检查、文件/上下文一致性及保留工作命令审计均通过。成本比较使用双方均成功的 **1186 个配对**；置信区间按原始 case 重采样，保留该 case 的三次重复关系。

### 现有结果

| 指标 | AgentTX | 时间后缀 |
| --- | ---: | ---: |
| 恢复合约与任务均通过 | 1200/1200 | 1186/1200 |
| 独立工作保留率，全部运行均值 | 100% | 43.10% |
| 恢复集合恰好等于受影响集合 | 1200/1200 | 30/1200 |
| 平均修复 API tokens，双方成功配对 | 145,358 | 464,582 |
| 平均完整流程耗时，双方成功配对 | 233.69 s | 303.87 s |

- 修复 token 减少 **68.71%**，95% CI 为 **65.41–71.76%**。
- 完整流程时间减少 **23.09%**，95% CI 为 **18.18–27.71%**。
- 模型修复阶段时间减少 **70.17%**。
- 时间后缀的 14 次失败均通过最终产物检查，但修复过程中重写了应保留的有效产物，因命令审计失败而未通过完整合约。

### 三个参数实验分别说明什么？

| 参数 | 检验的问题 | 现有结果 |
| --- | --- | --- |
| 执行长度 | 受影响集合不变，独立工作积累是否放大粗粒度恢复成本？ | 家族总体 token 节省 **87.97%** |
| 故障位置 | 影响集合不变，仅移动时间边界会怎样？ | 家族总体 token 节省 **88.49%** |
| 依赖密度 | 真正受影响的工作增多，保留机会如何变化？ | 家族总体 token 节省 **36.40%**，密集端点收益接近消失 |

依赖值为 1 时，两者保留集合相同，token 均值为 **327,894 与 328,922**；完整流程 AgentTX 为 **300.50 s**，时间后缀为 **212.48 s**。因果闭包已覆盖时间后缀，额外候选验证没有缩小修复集合，因而增加总耗时。

### 能支撑的结论

保留独立工作能明显减少实际模型修复成本；收益大小受可保留工作量影响。双方均使用 full context，有助于观察恢复边界本身的作用。成本优势不是每个参数点都成立。

## 4. 定位、依赖闭包与一致性：恢复过程是否做对了？

### 目的

在同一批系统运行中，分别检查选中的生产者、依赖闭包以及重建后的文件与可见历史。该实验对应当前论文 RQ3 的机制准确性测量。

### 现有结果

- 捕获到全部生成器依赖边。
- AgentTX 验证后定位 **1200/1200** 与注入生产者一致。
- **1200/1200** 恢复出精确影响集合，集合 precision / recall 均为 **100%**。
- **1200/1200** 保留未受影响文件字节，且可见上下文与文件恢复集合一致。
- 验证前候选排序的根因首位命中为 **0/1200**；根因排名范围 **12–144**，中位数 **60**。
- AgentTX 平均验证 **100** 个候选，P95 为 **160**；时间后缀平均检查 **34.9** 个边界。

### 能支撑的结论

当前受控工作负载中，捕获、隔离验证、依赖闭包和一致性恢复能够完成正确的恢复决策。准确率主要来自后续隔离验证，不能写成候选排序首位命中率，也不能解释为预先知道根因。这是机制正确性验证；移除同步机制的直接影响由下一项小消融测量。

## 5. 上下文小消融：只恢复文件够不够？

### 目的与设计

固定定位、因果闭包和文件重建方式，仅在文件恢复后保留失败前的旧工具观察，包括已撤销操作的动作/返回记录。完整 AgentTX 则同步移除对应的失效上下文。

选取覆盖执行长度、故障位置和依赖密度的 **12 个代表案例 × 3 次**，新增 **36 次**运行；按同一 case/repeat 复用已完成的 **36 次完整 AgentTX** 结果。

### 现有结果

| 指标 | 完整 AgentTX | 只恢复文件、保留旧观察 |
| --- | ---: | ---: |
| 最终任务完成 | 36/36 | 36/36 |
| 平均实际 API tokens | 116,538 | 160,004 |
| 平均完整流程耗时 | 243.54 s | 240.28 s |

保留旧观察使平均 token 成本增加约 **37.3%**。36 次新运行的实际用量均完整。

### 能支撑的结论

该代表性小样本支持上下文同步能够减少模型继续修复的成本；没有体现最终完成率或完整流程耗时优势。目前为配对均值，尚未完成该消融的置信区间分析。

保留旧观察是预定处理，所以消融组恢复时文件/历史一致性按设计为假。最终任务完成与恢复合约通过需要分开报告，不能把最终修好写成恢复状态原本一致。

## 6. SWE-Bench / Terminal-Bench：真实任务能否节省成本？

### 目的与设计

在真实任务工作区中先执行注入故障的恢复前缀：错误生产者、依赖产物和独立笔记交错；guard 发现注入故障后，各策略恢复，再由模型完成原始任务。它测量恢复策略对后续真实任务执行的影响。

- SWE-Bench Lite：**300 个任务 × 6 策略**，SWE-agent，每格一次尝试；1799/1800 格有完整结果。
- Terminal-Bench：**241 个任务 × 2 框架 × 6 策略**，共 2892 格，包含 3736 次原始、重试和修复尝试。
- 成功率使用全部计划任务作分母；TB 采用注册重试和环境修复后的最新结果。
- 成本比较要求双方最新结果通过完整合约、完整历史用量可核算，且 TB 配置兼容。费用累计包含记录到的失败、重试、修复和笔记 replay。

### 现有 token 成本结果

表内为 AgentTX 相对对照的累计 token 节省，括号为双方成功且成本完整的配对数。

| 对照 | SWE / SWE-agent | TB / SWE-agent | TB / Codex |
| --- | ---: | ---: | ---: |
| 不回滚 | 58.43%（275） | 24.70%（176） | 26.47%（200） |
| 时间检查点 | 17.55%（278） | 44.69%（175） | 25.39%（197） |
| 整分支回滚 | 27.86%（239） | 35.91%（177） | 28.43%（200） |
| Ideal | 1.47%（282） | 19.43%（188） | −10.85%（203） |
| Clean | 14.38%（264） | 36.57%（172） | 17.90%（198） |

三个常规对照在三个 workload/harness 组合上的九项比较，其 95% CI 下界均为正。相对 Ideal 的三个区间均跨零；TB/Codex 对 Clean 的区间也跨零，不能仅据均值判断这些参考组的稳定优势。

### 现有成功率结果

| 策略 | SWE / SWE-agent，分母 300 | TB / SWE-agent，分母 241 | TB / Codex，分母 241 |
| --- | ---: | ---: | ---: |
| AgentTX | 285 | 208 | 223 |
| 不回滚 | 282 | 203 | 224 |
| 时间检查点 | 284 | 206 | 224 |
| 整分支回滚 | 243 | 208 | 227 |
| Ideal | 289 | 207 | 222 |
| Clean | 273 | 206 | 225 |

### 能支撑的结论与范围

相对常规恢复策略，累计 token 成本有较稳定的下降；成功率没有跨工作负载和框架的一致优势。

AgentTX、Ideal、Clean 使用 compact context，常规对照使用 full context。因此真实任务收益包含恢复与上下文组织的共同作用；双方均为 full context 的受控实验更适合解释恢复边界本身。

这里的恢复故障由前缀注入，在原任务执行前被发现；不能把结果解释为对真实任务自然发生错误的通用根因定位成功率。逐任务与类别结果也存在反转，例如 TB/Codex 的 machine-learning/training 类别相对不回滚多消耗 10.54%（19 对），相对检查点多消耗 6.48%（20 对）。

## 7. 阶段耗时与 tracing 后端：代价花在哪里？

### 完整流程阶段测量

阶段均值来自两策略各自全部 1200 次运行，分母与双方成功配对的成本均值不同。

| 阶段平均耗时 | AgentTX | 时间后缀 |
| --- | ---: | ---: |
| 原始执行与记录 | 13.43 s | 13.25 s |
| 发现与应用恢复 | 136.44 s | 4.40 s |
| 模型修复 | 84.64 s | 286.88 s |
| 最终验收 | 0.17 s | 0.18 s |

AgentTX 的候选搜索平均占 **136.14 s**。它减少模型修复，却增加验证工作，解释了为什么 token 节省约 69%，完整流程耗时只下降约 23%。高依赖端点的额外搜索会使总时间增加。

原始执行与记录均值为 **138.31 ms/操作**，包含原始操作本身、tracing、快照和 ledger 更新，不能当作纯插桩开销。AgentTX 最终验证在全部运行中均小于 0.30 s。

### tracing 后端小实验

12-step 测量中，strace 为 **25.60 ms/step**，可选持久 eBPF 后端为 **61.39 ms/step**，两者在该探针中捕获相同的读取与 negative lookup 情况。

这组结果支持当前实现选择，是辅助性测量；当前主要性能优化空间仍在候选验证效率，不能把该小探针推广成任意工作负载上的后端性能结论。
